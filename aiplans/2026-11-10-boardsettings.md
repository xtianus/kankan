# Board settings and per-role model selection Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task, according to the execution method chosen by the user. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let users choose each agent type's implementation and review model/effort on Trello, with durable validation, clear feedback, and safe agent restarts between tasks.

**Architecture:** A pure `boardconfig` evaluator produces effective settings and a durable action journal; `boardsettings` connects it to Trello reads and retries. Separate modules handle catalog discovery, seeds, card construction, and isolated model checks. The existing workflow and launcher consume a pinned selection for each task and restart only the agent process when that selection differs.

**Tech Stack:** Python ≥ 3.10 standard library, Linux `flock`/`prctl`/`/proc`, Git ≥ 2.38, tmux ≥ 3.2, pytest and pytest-xdist, existing fake Trello and fake agents.

**Spec:** [Board settings functional specification](../aispecs/boardsettings_spec_functional.md) (F), [board settings technical specification](../aispecs/boardsettings_spec_technical.md) (T), and [Kanban requirements](../aispecs/kanban_requirements.md). The [initial functional](../aispecs/initial_spec_functional.md) and [initial technical](../aispecs/initial_spec_technical.md) specifications describe the implemented baseline. F§4 and T§4 describe its changes; do not merge the feature pair into the initial files.

**Status:** planned; no implementation performed. Both feature specifications have been updated with links to this plan and remain draft, not implemented.

## Global Constraints

- Minimum versions: Python 3.10, Git 2.38, tmux 3.2.
- Runtime uses only the standard library; pytest is a development dependency. Python indentation is four spaces.
- Everything is in English; user-facing text belongs in [messages.py](../kankan/messages.py).
- Setting keys are `implementation` and `review`; checklist names are adapter types; item names are `<model> · <effort>`.
- Models are ordered most powerful first, efforts highest first, preserving adapter order throughout. Ship no seeds.
- Local `settings_poll_seconds` defaults to 30; quiet-period eligibility is `Date − dateLastActivity ≥ 10 s`, following T§2's exact boundary.
- Seed keys are `1`–`9`, `a`–`z`, `A`–`Z`: at most 61 combinations per adapter.
- Adapter timeouts default to `exit_timeout_seconds=20`, `start_timeout_seconds=120`, `model_check_timeout_seconds=90`, `model_check_retry_seconds=600`. Tests override them with short values; only unit tests assert the defaults.
- In a launcher, model checks and `version_command` are polled child processes; the cycle never waits for them. Exit statuses are collected per PID, never with `waitpid(-1)`.
- Comments use `kankan:<op-id>`; help uses `kankan:help`. Retain the latest 10 marked comments authored by kankan, plus help and all people's comments.
- Tasks keep the selection with which they started. A checklist card has no default; seeds apply only before any valid value was recorded.
- Structural IDs, paths, credentials and `test_command` stay local. Board text never selects commands and never reaches a shell.
- Preserve Git ownership transactions, cross-type review, convergence, existing pane write rules, and the seat lease during a planned restart.
- Every eventual commit changing Trello endpoint use must include the matching revision of [kanban_requirements.md](../aispecs/kanban_requirements.md).
- Follow project commit rules: one final implementation commit after verification, then push to the required branch; no per-task commits or PR creation. This planning task does not commit or push.

## Review Focus

1. A model check finishes after a newer board edit: cache the result for its original pair/version, but never overwrite the new effective selection or its errors (Tasks 5, 7).
2. A person copies kankan's marker into a comment or sets `Error` first: never delete their comment or claim ownership of their label (Tasks 4, 5).
3. A settings-list read lacks trustworthy timestamps or races a newer read: defer evaluation, preserve current values, and retry without marking the edit handled (Tasks 3–5).
4. Catalog/seed writes from two projects race, or JSON serialization reorders models: retain both projects' changes and the user's model order (Tasks 1, 2, 7).
5. A role change restarts an agent while `HOLD`, a user move, recovery, stop, or takeover arrives: no stale task prompt, no lost WIP, and no signal to the launcher's process group (Tasks 8, 9).
6. The subreaper launcher reaps an adopted orphan while a model check runs: the check's exit status must never be taken, so a rejected pair can never be recorded as passed; Codex's shared daemon survives another seat's restart (Tasks 7, 9).

## Implementation decisions

- Represent a pair with immutable `adapters.ModelEffort(model: str, effort: str)`. Persist it as `{"model": ..., "effort": ...}`. A role setting's value maps adapter type to that pair; accepting a card replaces the entire role value only when every checklist is valid.
- Discover adapter types from non-metadata entries in the shipped/user/project adapter mappings, including types with no seats yet. Preserve shipped → user → project precedence. Adapter loading during evaluation is read-only; catalog refresh is an explicit preparation outside locks. Reload overrides at every evaluation.
- Normal startup prepares a missing/version-stale catalog; online fixing `doctor` refreshes it even for the same CLI version. Offline and `--no-fix` paths read available files without refresh or cache writes. `--no-fix` uses an in-memory evaluation and cached probe results, reporting unverified pairs instead of running a probe that creates files.
- Do not use `config.atomic_write_json` unchanged for adapter overrides/catalog mappings: it uses `sort_keys=True`, which destroys model order. Add a backwards-compatible keyword `sort_keys: bool = True` and use `False` for order-sensitive files. Existing state writers keep their current behavior.
- Thread response metadata through the request return value, never a mutable `client.last_response_date`. Concurrent responses must retain their own dates. Settings evaluation receives an immutable read envelope, not wall-clock time or a client.
- Use three separate phases: prepare adapters/probes outside locks; evaluate and persist actions under the project lock; dispatch short, serialized journal actions and acknowledge each success. Card construction holds its own lock across the build, taking the project lock only for short records and config changes. Never hold the project lock across terminal input, model discovery/check subprocesses, or process shutdown/start waits.
- Keep structural invalidity, model-check failure and label ownership as separate causes. Clearing one cause must not erase another or remove a pre-existing user `Error`. Losing state cannot establish ownership of a label already present.
- Pin a task's selection at claim time, after its model check passed outside the project lock; the claim comment names that pair and is never followed by a correction. An edit made later, including during the planned restart, applies from the next task (F§2, T§3 "Restart"). Post-restart revalidation covers ownership, ref/list, `HOLD`, user moves, stop and binding, never the settings.
- Every agent spawn except a planned restart (which uses the pair pinned at claim) reads the effective selection: the held card's role (review before implementation), otherwise `implementation`. If that role's pair has not passed and no held card needs it, spawn with the other role's passed pair; if neither passed, fail the start (abnormal exit, supervisor backoff). There is no launcher state without an agent (T§3 "Every start uses the values in force").
