# kankan Q&A agent pool — technical specification

**Status:** specified, not implemented; requires the board reader ([`boardreader_spec_technical.md`](boardreader_spec_technical.md)), implemented first.
**Date:** 2026-11-25
**Base:** [`initial_spec_technical.md`](initial_spec_technical.md) v1.3, [`questions_spec_technical.md`](questions_spec_technical.md), [`seat_spec_technical.md`](seat_spec_technical.md), [`stopall_spec_technical.md`](stopall_spec_technical.md) and [`boardreader_spec_technical.md`](boardreader_spec_technical.md); this feature changes them as listed in [§13](#13-changes-to-the-initial-technical-specification) and [§14](#14-changes-to-other-technical-specifications).
**Companion:** [`qapool_spec_functional.md`](qapool_spec_functional.md) — the behaviour this file implements; read it first.

**Split rule.** This file describes how kankan implements the feature; the functional file describes what users and agents observe. Section numbers are this feature's own.

## 1. Scope

A new module `kankan/qapool.py` holds the pool policy: cache readings and expiry ([§3](#3-prompt-cache-readings)), the routing round ([§5](#5-routing-round)), opening and closing agents ([§6](#6-opening-and-closing)), the answer record ([§5](#5-routing-round)) and the title prefixes ([§8](#8-title-prefixes)). `QaLauncher` runs in two roles: the **router** (`<type>-qa`), which also answers cards, and the **members** (`<type>-qa2`, …), which only answer the cards offered to them ([§4](#4-roles-and-offers)). A hidden command, `kankan statusline`, records Claude's cache expiry ([§3](#3-prompt-cache-readings)). Every Trello read goes through the board reader.

## 2. Seats and configuration

- **Names.** The seat pattern becomes `^[a-z]+-([0-9]+|qa([2-9]|[1-9][0-9]+)?)$` in `refstore` (inputs validated before reaching Git) and in `destroy`'s ref pattern. `seats.seat_type()` (the part before the last `-`) is unchanged. `qapool.router(cfg)` gives the registered `<type>-qa`, `qapool.members(cfg)` the registered `<type>-qaN`; every registered `qa` seat has the router's type (checked when a member is registered).
- **Registration.** A member is registered by the router only ([§6](#6-opening-and-closing)), with `role: qa`, no lists, and its worktree created like a seat worktree. The places that count or list seats for the user skip members: `seat_cap` and the per-type counts (as for every `qa` seat today), `kankan up` without arguments and `agents_cmd.registered_args`, the stop record and the autostart arguments (both keep `qa=<type>` only).
- **Starting a member.** `agents_cmd.start_member(project, seat)` starts the supervisor of a registered member under its exact seat name, registering nothing and without the preflight; the supervisor gives that name to every launcher it restarts. `seats.is_qa` matches the router and the members (today it matches only names ending in `-qa`), so `launcher.main` runs `QaLauncher` for both. `seats.acquire_qa(project, type, seat)` occupies the seat it is given (today it always occupies `<type>-qa`): the router registers itself as today; a member is refused (`config_error`, which the supervisor treats as fatal) when it is not registered, is marked for removal, or the pool is stopping ([§9](#9-stop-start-and-type-change)), so the supervisor of a closed member never brings it back. The router is refused the same way while the pool is stopping, so a supervisor restart of the router during a stop never reopens the pool; the commands that start the router clear the mark first ([§9](#9-stop-start-and-type-change)). `agents_cmd.agent` keeps refusing a member's name (`usage_error`, [§9](#9-stop-start-and-type-change)).
- **Configuration.** `config.json` gains `qa_prefix_warm` (default `🟢`) and `qa_prefix_cold` (default `⚪`): non-empty strings without whitespace, validated by `config`.
- **Adapters.** Each adapter gains `prompt_cache`: `{"expiry": "exact" | "estimated", "lifetime_minutes": <int>, "reporter": <name or null>}`. Defaults: Claude `{"expiry": "exact", "lifetime_minutes": 60, "reporter": "claude_status_line"}`, Codex `{"expiry": "estimated", "lifetime_minutes": 30, "reporter": null}`. `exact` requires a known reporter; the adapter validation refuses `exact` with none.

## 3. Prompt cache readings

**Reporter `claude_status_line`.** The launcher of a Q&A seat whose adapter names this reporter appends `--settings {"statusLine":{"type":"command","command":"<gcd>/kankan/bin/kankan statusline"}}` to the agent command (the wrapper of [initial technical §7.4](initial_spec_technical.md#74-identity-and-process-data), already first on the agent's `PATH`). Claude Code runs the status line command after every request of the agent, also in the middle of a turn, with the agent's environment and the worktree as working directory, and passes it a JSON object on standard input whose `prompt_cache` is `null` before the first request and then carries `expires_at` (Unix seconds: the request time plus the cache lifetime), `ttl` (a string such as `"1h"`) and `warm`; a `--settings` status line replaces the user's (Claude Code 2.1.332, observed on 2026-11-25 with a throwaway agent). `kankan statusline`:
1. identifies the seat as agent commands do (`KANKAN_SEAT`/`KANKAN_SESSION`, or the agent file), and does nothing more when it cannot;
2. writes `<gcd>/kankan/seats/<seat>.cache.json` atomically: `expires_at`, `ttl`, the agent's process ID and start time, and the time of the reading;
3. runs the user's own status line, if any, with the same standard input and working directory and a 5-second timeout, and prints its output: the first `statusLine` of type `command` in the worktree's `.claude/settings.local.json`, `.claude/settings.json`, then `~/.claude/settings.json` (Claude Code's precedence, the `--settings` override excepted);
4. always exits 0; an error is written to the audit log, never to the status line.

**Expiry.** `qapool.expiry(project, seat)` gives `(time, exact)`:
- `exact`: from `<seat>.cache.json` when it belongs to the seat's current agent process (same process ID and start time) and has a non-null `expires_at` (a past `expires_at` means cold);
- otherwise `estimated`: the end of the agent's last turn plus `lifetime_minutes`. The launcher records `turn_ended_at` in the seat state when a turn ends (a signal, a turn ending without one, or the agent ready after a typed turn); an agent without a finished turn since its start has no expiry and is cold.

A seat is **warm** when its expiry is in the future. An agent restart changes the process, so the reading no longer counts, and clears `turn_ended_at`: a restarted agent is cold.

## 4. Roles and offers

**Router.** The launcher of `<type>-qa` keeps every duty of today's Q&A launcher for its own conversation, replaces the idle claim of the top `Q&A` card (questions technical §4) with the routing round ([§5](#5-routing-round)) run every `qa_poll_seconds` in every state (also while its own agent answers), and owns the title prefixes ([§8](#8-title-prefixes)).

**Members.** The launcher of `<type>-qaN` never scans the `Q&A` list. It watches its own card as today (`poll_active`, through the board reader with `max_age(qa_poll_seconds)`) and takes the cards offered to it.

**Offers.** The router gives a card to a seat by writing `qa_offer` (`card`, `offer_id`, `at`) in that seat's state, under the **pool lock** (`<gcd>/kankan/qa-pool.lock`). A card has at most one outstanding offer: while a seat state names it in `qa_offer`, the card is not routed again, also when the seat is still starting. An offer is taken by the seat's launcher when it is in `idle` or `qa_waiting` and its pending answer, if any, is settled:
- an offer of the card it already holds is dropped (its own polling delivers the input);
- otherwise it ends its conversation (`qa.end`, the card stays in `Q&A`), sends the adapter's new-conversation command and claims the offered card (`qa.claim`, which re-checks under the project lock that the card is in `Q&A`, open, without `HOLD`, with no other holder); the first turn marks the items newer than the latest complete answer as `new` (`qa.first_turn`);
- an offer that cannot be taken (the card left, got `HOLD` or another holder) is dropped and logged; the router routes the card again at its next round.

An offer to a member that is gone ([§5](#5-routing-round) step 2) disappears with the member's seat state when the member is removed.

The router takes its own offers in-process. A seat clears `qa_offer` when it takes or drops it.

**Lock order.** Seat-removal lock → `up.lock` → Q&A lifecycle lock → pool lock → conversation lock → project lock → seat-state lock → answer-record lock → board-cache locks: the order of [seat technical §6](seat_spec_technical.md#6-completion) with the pool lock and the answer-record lock added. Each operation takes them in that order:
- **Choice** ([§5](#5-routing-round) step 4): lifecycle lock, pool lock, then for each write the project lock (configuration) or the seat-state lock (offer), each released after its write.
- **Answer completion** (`qa_answer`, conversation lock and project lock held as today): the answer-record lock last, for the `delivered` update.
- **Turn end** (launcher): the answer-record lock alone.
- **Removal** (`seatremove.complete`): the removal lock, then the conversation lock and the project lock to complete a pending operation ([§14](#14-changes-to-other-technical-specifications), seat §6), then the lifecycle lock, as today. It is never called while the caller holds the lifecycle lock or the pool lock: the router and the stopping commands release them first.
- **Stopping mark** ([§9](#9-stop-start-and-type-change)): lifecycle lock, then pool lock.

The pool lock and the answer-record lock (`<gcd>/kankan/qa-answered.lock`) are held only to read or rewrite their files, never across a Trello request, a process start or a seat removal.

## 5. Routing round

The router, every `qa_poll_seconds`:
1. **Reads**, through the board reader with `max_age(qa_poll_seconds)`: the board view and, per card in `Q&A`, `new_comments(after=<the card's checked mark>, card_id=…)`, served from the board-wide comment log ([board reader technical §7](boardreader_spec_technical.md#7-comment-log)) when the mark is not older than the log's horizon, otherwise by a read of that card's comments. There is no router cursor: each card keeps its own marks in the answer record (step 3). It reads the seat states, expiries and `qa` refs locally.
2. **Ended cards and gone members.** A pool member whose card left `Q&A`, was archived, deleted or got `HOLD` ends its conversation as today ([questions technical §4](questions_spec_technical.md#4-launcher)) and becomes available; the router closes it in step 5 unless step 4 gives it a card. A pool member is **gone** when its seat liveness is `free` past the startup deadline of its opening ([§6](#6-opening-and-closing); registered but never started, for example after a router crash between registering and starting it) or `dead`, and its supervisor no longer runs or gave up: the supervisor records `gave_up` in the seat's process record when it stops restarting the launcher, and the router checks the recorded supervisor by process ID, start time and boot ID, so a launcher between two supervisor restarts (liveness `dead` for the restart delay) is never taken as gone. The router marks a gone member for removal under the project lock after checking its liveness again, and removes it in step 5 ([§6](#6-opening-and-closing)): its pending operation is completed, its `qa` ref ended and its offer dropped with its state, so its card can be claimed and needs an agent again when it has inputs.
3. **Cards needing an agent.** The **answer record** (`<gcd>/kankan/qa-answered.json`, rewritten atomically under the answer-record lock) keeps per card:
   - `delivered`: what agents were given in turns that **ended**: `description` (true once a turn on the card ended, so a question asked only in the description counts as delivered), `comment` (the date of the newest comment given, a comment point of [board reader technical §3](boardreader_spec_technical.md#3-units-and-timestamps): comments are ordered by date, never by ID) and `attachments` (the IDs of the attachments given, as the conversation's `covered` set of [seat technical §8](seat_spec_technical.md#8-qa-first-turn-with-nothing-new) does: attachments are tracked by ID, never by date). A turn ends when its signal is accepted (an `answer` or `handoff` completed, a `fail`) or when the agent is ready again without a signal; the launcher updates `delivered` then with the inputs that turn was given (for a first turn, those its prompt marked as new; for a follow-up, those forwarded), and `qa_answer` updates it before deleting the pending operation, so an answer completed later (by a removal or a router start) counts once it is complete. A turn cut short because its agent was killed (an immediate stop, a crash, a restart) updates nothing, so its inputs still need an answer after the next start. A failed turn counts as delivered: the card waits for new input, as today ([questions §3.4](questions_spec_functional.md#34-errors)).
   - `answered`: the ID and date of the newest complete answer comment, updated by `qa_answer` when an answer completes; it is shown by `status` and used for seeding.
   - `checked`: the completeness point of the card's last `new_comments` call: the comment date up to which the card's comments are known.
   - `inputs`: every input by an input member (`notify.input_members`) found by a round and not yet delivered: each comment dated after `delivered.comment` and each attachment not in `delivered.attachments`, with its ID, kind and date. It is written in the same atomic write as `checked`, so moving `checked` past a comment never forgets it. A turn's end removes exactly the inputs that turn was given; inputs that arrived during the turn stay listed, also when the turn failed and its agent restarts or moves to another card.

   Each round updates `checked` and `inputs` for every card in `Q&A`, held or not, from step 1's reads and the attachments of the board view (attachment items of [board reader technical §2](boardreader_spec_technical.md#2-interface)). A card not in the record is seeded from one live thread read: `answered` from the newest comment carrying the answer marker that `qa._complete` accepts; `delivered` with `description` true, `comment` equal to that answer and `attachments` the attachments dated before it; `checked` the newest comment date; `inputs` the inputs after that answer. A card without any complete answer is seeded as never delivered (`description` false, no comment, no attachment). A card in `Q&A` without `HOLD` whose `qa` ref names no alive seat of the pool **needs an agent** when `delivered.description` is false and it has no `parked` handoff ref (a new card: its description is the question), or when its `inputs` is not empty; the new turn's prompt then marks everything after the latest answer as new, the inputs of a failed turn included. Its **wait key** is the date of its oldest input (the card's creation, from its ID, for a new card).

   **Reconciling with the thread.** Whenever a pool seat prompts a turn on a card (a first turn or a follow-up), it reads the card and its thread live, as today, and removes from `inputs` the entries listed before the live reads were sent that those reads no longer have: comments (by ID) missing from the thread, attachments missing from the card (deleted by the user; the comment log keeps them, [board reader technical §7](boardreader_spec_technical.md#7-comment-log)). Entries listed after the reads were sent stay for the next turn. A first turn also removes the entries that `qa.first_turn` counts as context rather than new (a comment dated before the latest complete answer, [functional §4.2](qapool_spec_functional.md#42-a-card-that-needs-an-agent)'s accepted limitation), so the record never keeps an entry that no turn will deliver. When nothing new remains, a first turn is not prompted ([seat technical §8](seat_spec_technical.md#8-qa-first-turn-with-nothing-new)) and a follow-up is not sent.

   **Holder delivery.** The holder of a card forwards, at every poll while it is ready, the inputs of its card listed in `inputs` besides those its own cursor finds, whatever that cursor's position, so an input found by a round while the holder was restarting or answering is delivered once and never lost. Entries of cards that are archived or no longer exist are dropped by `reconcile --fix`.
4. **Choice**, under the Q&A lifecycle lock and then the pool lock (the order of [§4](#4-roles-and-offers)), with no Trello request and no process start while holding them:
   - **Reservations.** A seat holding a card whose `inputs` is not empty is reserved for that card: its own polling delivers the input as a follow-up ([functional §4.2](qapool_spec_functional.md#42-a-card-that-needs-an-agent) rule 1), so it is offered no other card, even when it is cold. A card with an outstanding offer is skipped ([§4](#4-roles-and-offers)).
   - **Assignment**, the other cards needing an agent in wait-key order: the available seat with the lowest number (idle or `qa_waiting`, no pending answer, no outstanding offer, not reserved, cold or with an ended card); then a new member, registered and given the offer in this step and started after the locks are released ([§6](#6-opening-and-closing)); when every seat is busy or an opening failed in the previous round, the idle warm seat, not reserved, with the soonest expiry; otherwise the card waits. No member is opened while any seat of the pool is `limited` or the pool is stopping ([§9](#9-stop-start-and-type-change)).
5. **Closing.** When step 4 handled at least one card, every other idle cold member without an outstanding offer and not reserved is closed. In every round, the members whose card ended (step 2) and that step 4 gave no card are closed, and the gone members are removed.
6. **Prefixes** ([§8](#8-title-prefixes)).

## 6. Opening and closing

**Opening.** In step 4 of [§5](#5-routing-round), under the Q&A lifecycle lock and the pool lock: the router registers the lowest free `<type>-qaN` (configuration write) and writes the offer into its new seat state. After releasing both locks it starts the member with `agents_cmd.start_member` ([§2](#2-seats-and-configuration); the preflight and the model check of the `questions` pair are the router's). A member registered just before the pool was marked as stopping is refused by its own launcher ([§2](#2-seats-and-configuration)) and removed by the stopping command ([§9](#9-stop-start-and-type-change)). The member's launcher starts cold and takes the offer when ready. When the start raises, or the launcher does not reach `idle` within the startup deadline, the router logs `qa_open_failed`, closes the member as below, and the card falls back as in step 4 at the next round.

**Closing.** The router closes a member by marking it for graceful removal (`seatremove`'s mark, `removing: graceful`), never through `seatremove.remove` or `request_graceful`: those are the user's removal paths and also lower the autostart unit and the stop record ([seat technical §7](seat_spec_technical.md#7-autostart-and-stop-record)), which a member never appears in. The member's launcher exits from `idle`/`qa_waiting` once no answer is pending (`removal_drained`). At every round the router completes, outside its locks, the removal of each marked member whose launcher is gone (seat liveness `free`, or `dead` and gone as in [§5](#5-routing-round) step 2) with `seatremove.complete`, which completes the member's pending answer or handoff and then removes its worktree, seat ref, state and configuration entry ([§14](#14-changes-to-other-technical-specifications), seat §6). A removal that fails (Trello unreachable while completing) leaves the member registered and marked; the next round tries again. A member stopped by `kankan stop` or `kankan seat stop <type>-qa` is removed by that command or by its own launcher as it exits ([§9](#9-stop-start-and-type-change)). Members left registered after a crash are completed when the router starts.

## 7. Expiry note

`qa_answer` appends the note to the last chunk when it plans an answer (step 1 of [questions technical §6](questions_spec_technical.md#6-agent-commands)), so the note is part of the pending operation and a completed answer carries the note planned for it. For an `exact` expiry the time is the `expires_at` of the seat's current reading, written after the request that ran `kankan answer` (the requests that end the turn move the real expiry a few seconds later, never earlier); when there is no such reading or its `expires_at` is not in the future, the note is the estimated one: the planning time plus `lifetime_minutes`. The wording is `messages.QA_CACHE_EXACT` or `messages.QA_CACHE_ESTIMATED`. The time is shown as `HH:MM` in local time, with the zone's IANA name from `TZ`, `/etc/timezone` or the target of `/etc/localtime`, else the abbreviation of `time.strftime('%Z')`. The note counts towards the chunk budget. `handoff` gets no note.

## 8. Title prefixes

- **Record.** `<gcd>/kankan/title-prefixes.json`: card ID → the prefix kankan wrote (`"🟢"`, `"⚪"`, or any configured value). Only the router writes titles and the record.
- **Desired prefix**, per card at each round: warm while a seat of the pool holds the card and is warm (or answering); cold while it holds it and is cold, or once the card's conversation ended by a switch or a closing and the card is still in `Q&A`; none when the card left `Q&A`, is archived, or was never held. A card that does not need a change is not touched.
- **Write.** The router reads the card live through the board reader, computes the title without the recorded prefix (if the title no longer starts with the recorded prefix and a space, the user edited it: the record is dropped and that title is the base), and writes `desired + " " + base`, or `base`, with `TrelloClient.set_card_name` (C11). The record is updated after the write is confirmed; a crash in between leaves a prefix kankan does not know, which it then treats as the user's text.
- **Start and stop.** When the router starts, it removes every recorded prefix ([§9](#9-stop-start-and-type-change)). A graceful stop of the router writes the cold prefix on every card it recorded warm before exiting; an immediate stop does not, and the next start removes them.
- **Plain titles.** `qapool.plain_title(paths, card)` removes a recorded prefix; `agentcmds.task` (`card.title`), `integrate` (the merge commit title), `diag` (status and claims) and every comment kankan writes with a card title use it.

## 9. Stop, start and type change

**Router start** (launcher start of `<type>-qa`, also after a reboot), refused while the stopping mark is set ([§2](#2-seats-and-configuration)): under the Q&A lifecycle lock, (1) completes the pending answer or handoff of its own conversations with its own lease (`qa_answer.complete_pending` without a signal, which updates `delivered`) and (2) ends its own `qa` refs (the cards stay in `Q&A`; the conversation directories go as today); then, with the lifecycle lock released, (3) removes every registered member that is not alive: marked or gone ([§5](#5-routing-round) step 2), which after a reboot is every member (`seatremove.complete`, which completes the member's pending operations before ending its conversations and takes its own locks), (4) removes the recorded prefixes and (5) runs its first routing round. No member can open meanwhile: only the router opens them. Members whose seat is alive (a launcher restart of the router alone, by its supervisor) are left alone: they keep their cards and complete their own pending operations, so the start never touches a conversation whose launcher runs.

**Stopping mark.** `<gcd>/kankan/qa-pool.json` holds `stopping` (true or false), written under the lifecycle lock and the pool lock. While it is set the router opens no member, and neither a member's nor the router's launcher starts ([§2](#2-seats-and-configuration)). It is cleared only by the commands that start the router, under the same locks and before they start it: `kankan start`, `kankan up` (also when the autostart unit runs it), `kankan agent <type> --qa` and `kankan seat start <type>-qa`; a type change clears it only once the old pool is removed. A stop interrupted by a crash therefore leaves the pool stopped until one of these commands runs.

**Stop.** `stopall` and `seat stop <type>-qa`, once the user confirmed: (1) set the stopping mark; (2) take the inventory of the pool's seats again, so a member registered after the first inventory is included; (3) for a graceful stop, mark every member for graceful removal (the closing mark of [§6](#6-opening-and-closing)); (4) stop every seat of the pool, gracefully or with `seat recover --kill`; (5) remove with `seatremove.complete` every member after an immediate stop (which completes the answer it was posting first, [§14](#14-changes-to-other-technical-specifications) seat §6), and after a graceful stop the members not running at that moment. A member whose removal fails (Trello unreachable while completing its answer) stays registered and is reported; the next router start completes and removes it. A member stopped gracefully finishes its answer and then completes its own removal when its launcher exits, as the launcher of a seat marked `removing: graceful` does at shutdown ([seat technical §5](seat_spec_technical.md#seat-behaviour-while-removing)). The stop record keeps `qa=<type>`, so `kankan start` starts only the router.

**Type change.** `kankan up qa=<other>` (also from the autostart unit) and `agent <other> --qa` with a pool of another type, under `up.lock`: set the stopping mark, kill every seat of the pool (`seat recover --kill`), release `up.lock` and remove them all with `seatremove.complete`, the members first and the old router last, so a rerun after a failure still finds the old pool through any registered `qa` seat of the other type, (as `agents_cmd.resume_removals` does), which completes the answers and handoffs they were posting ([§14](#14-changes-to-other-technical-specifications) seat §6); a turn killed before its answer was planned updates nothing, so the new pool answers its question. When a removal fails, the command stops with `needs_action` naming the seat and its error, before registering the new router, the stopping mark staying set; a rerun resumes the removals. Otherwise, under `up.lock` again, it checks that no seat of the old pool is registered (a concurrent command may have changed the pool: it then stops with `needs_action`), registers `<other>-qa`, clears the stopping mark and starts it. `qa.replace_seat`, the replacement record `qa-replacing.json` and the conversation takeover are removed; `reconcile` keeps reporting a `qa` ref whose owner is not registered (`qa_owner_unregistered`), which the next router start ends.

**Seat commands.** `cli` refuses `seat start`, `seat stop` and `seat remove` on a member (`usage_error`, naming the router); on the router, `seat stop` stops the pool, `seat start` starts the router, `seat remove` removes the members and then the router.

## 10. Trello usage

One revision of [`kanban_requirements.md`](kanban_requirements.md), made in the implementation commit:
- **C11 (SHOULD):** update a card's title. Used for the Q&A title prefix. There is no conditional update: a title edit made by the user in the same moment can be overwritten, or overwrite the prefix (G8). Renaming a card does not notify its watchers (checked by the user on 2026-11-25). `PUT /1/cards/{id}` (`name`).
- **C1 (assumption added):** a card's creation time is the first 8 hexadecimal digits of its ID (Trello object IDs), used for the wait key of a new card ([§5](#5-routing-round) step 3). The ordering of comment action IDs that the answer record relies on is recorded by the board reader's M7 ([board reader technical §9](boardreader_spec_technical.md#9-trello-usage)).

The routing round adds no request of its own beyond the board reader's shared reads, plus one live thread read per card seeded into the answer record and one live card read and one write per prefix change.

## 11. Status

`diag.status` lists the pool: per seat, its card (shortLink and plain title), launcher state, and cache (`warm until HH:MM`, `exact` or `estimated`, or `cold`); and the cards needing an agent with their wait key. `--json` gives the same fields.

## 12. Tests

- **Unit:** the seat pattern; `expiry` (exact reading of the current process, a reading of a previous process ignored, estimated from `turn_ended_at`, cold without a turn); the choice of [§5](#5-routing-round) step 4 with every combination of warm, cold, busy, ended and limited seats; wait-key order; closing only after a search; a member whose card ended given a card in the same round instead of being closed; a gone member (supervisor gone, or `gave_up`) removed, its offer dropped and its card routed again, and a member between two supervisor restarts left alone; the answer record and its seeding (complete and cut-short answers, inputs after the latest answer); `delivered` updated at a turn's end and not for a turn whose agent was killed; `inputs` kept across rounds in which the card gets no agent and across a router restart; a comment B arriving during a turn on comment A, the turn failing and the holder restarting with its cursor past B: B delivered once, from the record; an input deleted before a turn removed by the reconciliation, with no prompt; attachments tracked by ID (two with the same date); a description-only card answered and then idle not needing an agent; reservations (a cold holder with a listed follow-up is offered no other card) and one outstanding offer per card across two rounds; prefix computation (record, user edit, several characters, removal); the note's wording, time and zone, and its place in the chunk budget; `kankan statusline` (reading written, the user's status line chained from each settings file, no seat, a failing user command).
- **Integration** (private tmux server, fake agents in Q&A mode, fake Trello): the acceptance tests of [functional §8](qapool_spec_functional.md#8-acceptance-tests). The fake agent writes cache readings through a fake status line; tests set lifetimes in seconds to make agents go cold.
- **Locks:** concurrent member registration, answer completion and member removal finish without a deadlock; `seatremove.complete` is never called with the lifecycle or pool lock held.
- **Start path:** a member started through the supervisor reaches `QaLauncher` under its own name, survives a launcher restart under that name, and is refused after its removal and while the pool is stopping.
- **Stop:** a stop between a member's registration and its start leaves no member registered or running; a router launcher restarted by its supervisor during a stop refuses to start, and `kankan start` clears the mark; an immediate stop of a member posting an answer completes the answer as the member is removed, and with Trello unreachable leaves the member registered for the next router start.
- **Type change:** the answer of a killed member is completed by its removal; a failed removal stops before `<other>-qa` is registered and a rerun finishes.
- **Crash points:** between registering a member and starting it; the existing `qa_after_turn_saved` point followed by an immediate stop and a start (the question is answered once); between writing an offer and taking it; between ending the old conversation and claiming the offered card; between a prefix write and its record update.
- **Live agents run** ([developer manual §3.5](../docs/developer-manual.md#35-live-run-with-real-agents)): two Q&A cards answered by two Claude agents, the exact note and the warm and cold prefixes, a closing after expiry with a short lifetime; with Codex, the estimated note.

**Documentation.** The implementation rewrites the Q&A part of the user manual ([`docs/user-manual.md`](../docs/user-manual.md) §5.3, “Questions: `Q&A` cards”): the dynamic pool (agents opened and closed with their prompt cache, which card goes to which agent, the expiry note) together with the meaning of the title prefixes (`🟢 ` warm, `⚪ ` presumed expired, none when no agent took the card, and that kankan strips only the prefix it wrote).

- **§3–§4 Coverage.** `qa.newest` and `qa._comment_covered` order comments by date (from the thread, which carries each comment's date), not by action ID, which within one second is not ordered by creation ([board reader technical §3](boardreader_spec_technical.md#3-units-and-timestamps)); `covered.comment` keeps naming a comment by ID, and its date is looked up in the thread.

## 15. Accepted limitations

- An immediate stop leaves warm prefixes on the cards until the next router start removes them.
- A crash between a prefix write and its record leaves a prefix kankan treats as the user's text.
- A comment posted while an answer was being written, followed by a stop and start, counts as answered ([functional §4.2](qapool_spec_functional.md#42-a-card-that-needs-an-agent)).
- A comment or attachment deleted by the user while it is listed in the answer record can make an available agent clear its session and take the card, only to find nothing new and not be prompted ([§5](#5-routing-round) step 3).
- A member that cannot complete its pending answer at removal (Trello unreachable) stays registered, idle, until a later round, stop or router start removes it.
- An estimated expiry can be wrong in both directions: a card may go to a new agent although the old cache was still warm, or stay with an agent whose cache already expired.
