# Project notes

## Specifications

- The specification of kankan, the CLI that coordinates Claude Code and Codex agents through a Trello board, is in two files with one shared section numbering: [`aispecs/initial_spec_functional.md`](../aispecs/initial_spec_functional.md) (what users and agents observe) and [`aispecs/initial_spec_technical.md`](../aispecs/initial_spec_technical.md) (how kankan implements it). A "spec §n" reference points to whichever file holds section n. They are the initial specification, part of the specification, which is the set of files in `aispecs/`: each feature has its own pair `aispecs/<feature>_spec_{functional,technical}.md` (currently [board settings](../aispecs/boardsettings_spec_functional.md), implemented locally, the remaining release observation gate listed in its status; and [questions (Q&A)](../aispecs/questions_spec_functional.md), implemented locally, the live agents run with the Q&A dialogue outstanding) with its own numbering and a chapter stating how it changes the initial behaviour; feature pairs are never merged into the initial files.
- [`aispecs/kanban_requirements.md`](../aispecs/kanban_requirements.md) lists the Kanban API capabilities kankan needs, mapped to the Trello endpoints it uses. It is the reference for anyone writing an adapter for a Trello alternative.
- Implementation plans live in `aiplans/`. The user manual is [`docs/user-manual.md`](../docs/user-manual.md), the developer manual (tests, live Trello test board) is [`docs/developer-manual.md`](../docs/developer-manual.md); observed agent screens and behaviours are in [`docs/adapter-notes.md`](../docs/adapter-notes.md).

## Conventions

- Python code uses 4-space indentation (PEP 8), overriding the global tabs rule.
- Everything is in English: code, comments, specs, plans, user manual and user-facing messages. User-facing texts live in `kankan/messages.py`.
- Runtime code is standard library only, Python ≥ 3.10 (no `datetime.UTC`, `StrEnum`, `tomllib`...).

## Rules

- Before every commit that adds a call to a Trello API endpoint, changes how an endpoint is used, or stops using one, revise [`aispecs/kanban_requirements.md`](../aispecs/kanban_requirements.md) so that its capability tables and endpoint mappings match the code. The commit must include that revision.

## Architecture

- Module map: `refstore` (only module touching `refs/agent-*`), `trello` (only module talking to Trello), `config`/`properties`/`auditlog`, `seats`/`seatstate`/`procutil`, `cards` (transitions, convergence), `workflow` (choice, claims, `tick`), `integrate` (sync, verify, integrate, review done, block, resolve), `agentcmds` (agent commands), `launcher`/`supervisor`/`forward`/`tmux`/`adapters`, `agents_cmd` (agent, up, autostart), `attachments` (task inputs, download cache; called by `task` outside the lock), `diag` (status, claims, reconcile, admin), `doctor` (checks, fixes, preflight), `init`, `cli`.
- The agents integrate into `cfg.integration_branch` (default `kankan-agents`; old configs with `main_branch` are read as an alias); `cfg.user_branch` is the user's. Only `integrate` moves/pushes the integration branch (`pre-push` hook + `KANKAN_PUSH=1`); user work enters through merge-request cards (`integrate.merge_request`, SHA pinned at request time). The JSON key `main`, `push_main` and `main_moved` keep their names for compatibility.
- Codex 0.167 runs shell commands through a shared `codex app-server --managed-daemon`: they get the daemon's environment (login PATH, no `KANKAN_*`). Agent commands therefore fall back to `<worktree git dir>/kankan-agent.json` (written by the launcher), and `kankan` must be on the login PATH.
- `build.code_id()` hashes the kankan package; the launcher stores it in the seat file and agent commands refuse to run with different code (editable installs make this likely while developing kankan).
- Trello facts: attachment downloads answer 200 without a redirect; an upload's `fileName` is stable across renames; `mimeType` can be null. Checklists (observed 2026-11-10 on the test board): `checklists=all` on the board read gives a top-level array with `idCard` and item `state` (`complete`/`incomplete`), on `GET /1/lists/{id}/cards` it nests them per card; `POST /1/checklists/{id}/checkItems` accepts `checked=true`; ticking and unticking (`PUT /1/cards/{id}/checkItem/{idCheckItem}` `state`) update the card's `dateLastActivity`; both `DELETE /1/cards/{id}/actions/{idAction}/comments` and `DELETE /1/actions/{id}` delete a comment; responses carry a `Date` header.
- `TrelloClient` never follows redirects automatically (`_OPENER` with a no-redirect handler) and sends the credential with `add_unredirected_header`: a redirected JSON call fails; `download` follows at most 3 redirects itself, with the credential only on the `trello_base_url` origin and never downgrading https to http (`_redirect_auth`). Download URLs are validated and requested on `trello_base_url`.
- `attachments` (spec §13.3) is the policy of card attachments as task inputs; `agentcmds.task` calls `attachments.for_task`. Uploads by `notify.input_members` (board members minus kankan's account) are downloaded to `<gcd>/kankan/attachments/<shortLink>/<att-id>/<sanitized fileName>`. Every change inside a card's directory happens under the per-card attachment lock (`<gcd>/kankan/attachment-locks/<shortLink>.lock`, ordered after the project lock); `task` never takes the project lock. `cards.delete_integrated_ref` is the only way an integrated ref is deleted in `Done`. `attachments.discard` never waits (timeout 0) and never follows symlinks; a `task` holding the lock deletes the directory itself when its `still_held` check returns `Hold.GONE` (ref deleted), and never for `Hold.OTHER` (another owner or phase, or an unreadable ref: the copies may be another seat's). A ref deleted after the `task`'s final check but before it releases the lock leaves the directory behind (`discard` found the lock busy); `reconcile --fix` removes it. Names are sanitized to at most 255 UTF-8 bytes; the attachment directories are created with mode 0700; once a download hop leaves the API origin, no later hop carries the credential.
- kankan acts through its own Trello account (`cfg.kankan_member_id`, the token's owner). `notify.mention` mentions a card's creator, or the board's admins for cards kankan created; `notify.answers` forwards comments by board members other than kankan's account. A person's own token is unsupported (Trello never notifies anyone about their own comments, and their answers would be ignored): `init` warns, `doctor` gives a manual step.
- `doctor` checks and fixes the installation and project; its offline subset is the `up`/`agent` preflight. The launcher and `agent` put `<gcd>/kankan/bin` (only a `kankan` wrapper running `sys.executable -m kankan`) first on the agents' `PATH` (`agents_cmd.agent_path`): never the interpreter's own directory, which would shadow the project's python/pip.
- `workflow.tick(project, lease)` is one launcher iteration without the agent (convergence, choice, preparation); the hidden `kankan tick --seat <s>` runs it for debugging.
- Seat state (`<gcd>/kankan/seats/<seat>.state.json`) is changed only through `seatstate.update_state`.
- The launcher shares the pane's terminal with the agent: it never prints while the agent runs; events go to `<gcd>/kankan/log.jsonl`.
- Card refs carry `from_list` only while a Trello move is unconfirmed: after a verified move `cards.confirm_move` rewrites the ref without it, so convergence moves a card only from its recorded source and never replays a move over a later human move.
- Transitions of held cards (`impl`/`review`) by a seat require the card to be open and in its expected list; only the user-move parking (`cause` `user_*`) is exempt. `integrate` and review `done` apply the same rule and re-check seat ownership and task identity under the project lock.
- The launcher checks its seat lease every poll interval and exits when `seat recover` revoked it.
- `seat recover --kill` terminates only the recorded processes (pid + start time); a whole session is terminated only when it is the recorded supervisor-led pane session.
- Seat recovery terminates the processes of the recorded pane session only when that session was created by a kankan supervisor (`KANKAN_SUPERVISOR_PID` equals the session id) and the session leader's start time still matches; otherwise it kills nothing.

## Testing

- Tests use a fake Trello server (`tests/fakes/fake_trello.py`, with fault injection), a scripted fake agent (`tests/fakes/fake_agent.py`, installed as `claude`/`codex` on a temporary PATH) and private tmux servers (`KANKAN_TMUX_SOCKET`).
- Run the suite in parallel and in its own session: `setsid -w .venv/bin/python -m pytest -q -n auto` (pytest-xdist; each test has its own temp dir, HOME and tmux socket). Tests skip `kankan init`'s settle wait (conftest).
- Run the suite in its own session (`setsid -w .venv/bin/python -m pytest -q`): recovery tests kill process sessions. `-m "not slow"` skips the tmux process-chain tests.
- Tests set `KANKAN_SKIP_PREFLIGHT=1` (autouse); `tests/test_doctor.py` unsets it where it matters. `tests/helpers.bind_project` binds with `integration_branch="main"`; new tests pass `integration_branch="kankan-agents"`.
- `python -m tests.live.agents_e2e` is a manual live run with real Claude Code and Codex agents on the test board ([developer manual §3.5](../docs/developer-manual.md#35-live-run-with-real-agents)); it is never collected by pytest. Its helpers (`tests/live/e2e_support.py`) are tested in `tests/test_e2e_support.py`.
- Never call `monkeypatch.undo()` in a test: it also undoes the autouse isolated HOME.
- The fake Trello server serves attachment uploads (`upload`, `remove_attachment`, `redirect_download`, the `truncate` fault, downloads counted in `downloads` (racy when the client aborts a too-large download: assert on `auth_log`/`requests` instead), a `404` fault echoing the credential, `auth_log` records whether each request carried the credential); the `external_host` fixture (`tests/fakes/external_host.py`) is an HTTP server on `localhost`, another origin than the fake's `127.0.0.1`, for redirect tests.
- Live Trello tests (`-m trello_live`) need `~/.config/kankan/test.properties` or `KANKAN_TEST_BOARD_URL` + `KANKAN_TEST_CREDENTIALS`, and a board whose description contains `kankan-test-board`.

## Board settings architecture

- `boardconfig` evaluates immutable Trello read envelopes without I/O or local time. `boardsettings` serializes evaluation under the project lock, persists effective values and action intents before feedback, and reserves the shared settings-list poll. Schema/input fingerprints and revisions keep feedback and probe results tied to the edit and CLI version that produced them. Missing server/activity dates defer evaluation; an unavailable settings list preserves values.
- Lock order: settings construction lock → short project lock; feedback writer lock → project lock for individual feedback actions. Catalog/probe preparation and terminal seed questions run outside project locks. User seed and cache writes re-read under their own user-level locks and atomically replace files. Ordered model mappings use `sort_keys=False`. `seed` is the adapter JSON key; no adapter ships one.
- `modelcheck` polls isolated child processes and caches results per type/version/model/effort. A timeout is unverified and carries only a retry deadline. Read-only lookup starts no child and writes nothing. `model_catalog` prepares versioned catalogs explicitly; evaluation only reads them.
- Workflow preparation pins the pair at claim and defers publishing a task ID until activation. Activation checks seat/ref/list/HOLD/stop/binding. A planned launcher restart retains the seat lease and work, uses individual PID signals, preserves adapter-listed shared daemons, and starts the pinned pair. The launcher is a subreaper; adopted processes are reaped by PID, excluding all Popen-owned children, so model-check exit codes remain available. Running selection is published at readiness.

- Shared CLI-version and catalog observations carry ordering tokens, so a late completion cannot restore an older selection or check result. Timed-out children remain owned by their Popen objects and are polled after cancellation; no timeout path waits indefinitely for a child. Probe directories ignore inherited TMPDIR and are validated against repository/instruction ancestors.
- The launcher keeps a claimed but not yet activated task on `Launcher.prepared` (with its pinned pair) until `workflow.activate_task` succeeds; it never ticks meanwhile. Activation and the pre-prompt recheck (`refresh_task`) follow tick error handling: transient errors retry at `poll_seconds`, `NOT_OWNER` exits normally, `CONFIG_ERROR` stops. A stop before the prompt gives a fresh claim back (`workflow.release_unsent`); resumed or dirty work stays held.
- Per-second launcher work never ends a task on errors: `Launcher.refresh_settings` logs a config/settings error once and sets `stop_after_task` for `CONFIG_ERROR`. `boardsettings.poll` pre-checks the shared reservation without the project lock; unchanged cached check results are re-recorded at most once per settings poll; `procutil.reap_adopted` peeks with `waitid(WNOWAIT)` before scanning `/proc`.
- A seed that the Codex catalog no longer lists is moved to `Adapter.stale_seeds` and counts as missing (the seed question replaces it); only explicit `models` overrides make an invalid seed a `config_error`. `unavailable` entries in `<seat>.proc.json` always carry a start time; entries without one are never treated as alive.

## Q&A (questions) architecture

- The Q&A seat `<type>-qa` (`SeatConfig.role == "qa"`, no lists, own worktree; seat names match `^[a-z]+-([0-9]+|qa)$`, at most one registered) serves the `Q&A` list (`cfg.qa_list`, optional: a missing or archived list stops only the Q&A seat). `launcher.main` builds a `QaLauncher` (`kankan/qa_launcher.py`) for a seat ending in `-qa`; it overrides the base launcher's hooks and adds the state `qa_waiting` (follow-up polling every `qa_poll_seconds`, default 30; each poll there also reads the `Q&A` list). Work seats never take `Q&A` cards and count only `work` seats.
- `kankan/qa.py` is the conversation policy (record, claim, end, inputs and `new`, turns, handoff transition, seat replacement); `kankan/qa_answer.py` posts (chunking, pending operation, `answer`, `handoff`, commit check). Q&A transitions use `refstore` transactions that verify the seat ref, not `cards.transition`. Card ref phase `qa` carries `conversation` and `covered`; a handoff parks the card with `cause: handoff`, `pos: bottom`, `handoff` (summary comment IDs), copied into the `impl` ref by the implementation claim.
- Files: `<gcd>/kankan/qa.json` (cards that were Q&A cards, exempt from `reconcile`'s `done_without_merge`; an implementation claim removes the entry, `reconcile --fix` those of archived or deleted cards, read before the project lock), `<gcd>/kankan/qa/<conversation>/` with `op.lock`, `turn.json` (turn token, delivered inputs, first-turn context, run ID) and `pending.json` (a chunked answer or handoff being posted). The directory is deleted at the end of a conversation that was not handed off, by `cards.delete_integrated_ref`, by a new claim of a card whose parked ref names an older conversation, or by `reconcile --fix`.
- Lock order: `up.lock` (held by `kankan up` while it registers the Q&A seat) → Q&A lifecycle lock (`<gcd>/kankan/qa-lifecycle.lock`: seat replacements and `seat remove <type>-qa`) → conversation lock (`qa/<conversation>/op.lock`; `qa.LockBusy` when not taken in time) → project lock → seat-state lock. `fail` in a Q&A task runs its validation, card read, label, comment and signal under the conversation lock, so no turn starts meanwhile. A Q&A hold of the project lock contains at most one card read, one Git transaction and one move with its verification read; chunks are posted, attachments downloaded and the agent awaited without it. A work seat's implementation claim holds the project lock through its board read, card read, move, verification read, claim comment and HOLD recheck (unchanged by the feature).
- Turns: every prompt gets a turn token saved in `turn.json` and the seat task before the pane write; `answer`, `handoff` and (optionally, `--turn`) `fail` carry it, signals carry it, and `QaLauncher.take_signal` drops a signal of another turn. A restart (launcher start, agent restart for a new pair, seat replacement) writes `QA_RESTART` only when the conversation has uncovered inputs or no `covered` yet; otherwise it goes to `qa_waiting` silently and the next delivery uses `QA_RESTART_FOLLOWUP`. A turn ending without a signal, and every delivery or typed turn, first tries the conversation lock without waiting and completes the turn's `pending.json` (`QaLauncher.settle_pending`: a completed answer is no `Error`; a busy lock means the command is still posting). A pending operation of an older turn is completed (without a signal), never dropped. `task`, `fail` and `note` read the card again and give `not_owner` once it left `Q&A`, is archived or on `HOLD`, before the launcher's poll deletes the ref. `new` after a conversation restart is decided by Trello dates, never the local clock. The commit check counts only commit-creating `HEAD` reflog entries (commit, merge, cherry-pick, revert, rebase, am, pull) since the claim.
- `HOLD` on a handed-off card still in `Q&A` with its move outstanding cancels the handoff: convergence (`cards._cancel_handoff_move`) drops `from_list`/`pos`, sets `target_list` to `Q&A` and does not move; the card is taken again as a new conversation once `HOLD` is removed.
- Accepted window: a crash after the handoff move but before `confirm_move`, followed by the user dragging the card back into `Q&A` before any convergence, moves it to `Backlog` once more (the same window as `cards.transition`); a second drag sticks.
- Accepted delay: an idle Q&A launcher does not claim while a CLI-version or catalog check of its type runs (`QaLauncher.idle` checks again at the next step); the check does not block the step loop, so a claim waits for its completion only.
- Seat replacement (`qa.replace_seat`, run by `agent --qa`, `up qa=<type>` and, completing only, by the new seat's launcher): (1) the old seat must be `dead` or `free` with no survivor; (2) one configuration write swaps the old entry for the new one, so at most one Q&A seat is ever registered and `seats.acquire_qa` refuses the old name (an old supervisor stops on `FATAL_EXIT`); it also writes the replacement record `<gcd>/kankan/qa-replacing.json` (old, new); the later stages are identified from the `qa` ref's owner, the old seat ref and, while the record names the pair, the old worktree and seat files (a plain `seat remove` is no replacement): (3) the `qa` ref is rewritten with the new owner, verifying the old ref value and the old seat ref; (4) the old seat ref is deleted; (5) the old seat's label causes for the moved cards go to the new seat, the old worktree (if clean), seat files and the record are removed. A record whose new seat is neither registered nor starting is dropped (`qa.drop_stale_record`, also by `seat remove <type>-qa`). `task` deletes the files of an ended conversation only under the project lock (tried without waiting) and only while no newer task or conversation of the card exists. Replacements hold the lifecycle lock and every stage re-checks that its destination is the registered Q&A seat. With no Q&A seat registered, a starting seat registers itself and completes the leftovers of another one; `reconcile` reports `qa_owner_unregistered` for a `qa` ref whose owner is not registered.
- Shared Q&A helpers, one definition each: `qa.QA_MARKER` (the answer/handoff chunk marker, read by `qa.first_turn` and by `task`'s thread and handoff summary), `qa.handed_off` (the handoff transition happened; `qa_answer` also passes the posted summary IDs, the launcher does not know them), `worktrees.reflog_subjects` (the `HEAD` reflog, used by `reflog_length` and the commit check), and the ownership helpers `qa.ours`, `qa.check_seat`, `qa.drop_orphan`, `cards.parse_refs`, used across modules.
- `boardconfig.roles(paths)` (the active roles: seeds, preflight, setting cards created, doctor checks and probes) adds `questions` only while a `qa` seat is registered, and logs an unreadable configuration (`roles_config_unreadable`); the evaluation always uses `adapters.ROLES`, so the `questions` card never becomes an unknown setting; a launcher compares only its `own_roles()`. `up qa=<type>` and `agent --qa` check the `Q&A` list, replace a Q&A seat of another type and register `<type>-qa` (`agents_cmd._register_qa_seat`) before the `questions` seed preflight, so a start refused for a missing seed leaves the seat registered (status `free`) and `init`/`doctor` then ask for the seed and create the `questions` card.
- Tests: `tests/test_qa*.py`; `tests/test_qa_e2e.py` runs the Q&A seat with work seats end to end and the independence test (fake Trello `delay` fault, project-lock holds measured by polling the lock file). Fake agent steps substitute `{turn}` and `{file}`. Launcher tests that assert nothing happened wait for poll cycles counted in the fake Trello request log (`wait_card_polls`: comment reads of the active card; `wait_board_polls`: idle board reads), not for fixed times; only states without any Trello poll (`limited`, an ended conversation) keep a short sleep.

## Card instructions (agent sections)

- `kankan/cardsections.py` is the pure parser of a card description: specification (text before the first `agent:` heading candidate), agent sections, problems; `for_seat` selects a seat's sections; `help_text` builds the `Instructions` card. `adapter_types` refuses an adapter named `all` (reserved target).
- `kankan task` returns `desc` without agent sections for `impl`, `review` and `hold_wip`, plus `card_instructions` / `card_instructions_error` for `impl` and `review`; Q&A cards are never parsed.
- Invalid headings are checked in `workflow._check_sections`, first thing in `claim_impl` / `claim_review` (inside the claim's project lock). The report lives in the project-level `<gcd>/kankan/card-sections.json` (`cardsections_feedback`), never in seat states: pending actions (comment, add/remove `Error`) are performed by `drain` one per lock hold after a C1 reread; `sweep` only schedules removals, `drain` confirms them; both never raise. Work launchers call them in `tick` and `periodic_board_check`; the Q&A launcher does not.
- `waiting_reasons` gives `invalid_headings` from the board read alone, independent of the record.
- The `Instructions` card is kankan-owned: `settings_setup.ensure_instructions_card` creates it at the top of the `kankan` list, rewrites it (C9, `TrelloClient.set_card_desc`) and moves it back to the top when another card has a lower `pos` (C3 within the list); `boardconfig.evaluate` reserves its name under the pseudo-key `instructions` (duplicates get `Error`).
